# Implementation Plan

- [ ] 1. 建立后端基础运行环境
- [ ] 1.1 初始化后端应用、依赖与测试入口
  - 建立可启动的 FastAPI 后端应用和测试配置。
  - 配置数据库连接、应用配置读取和测试夹具所需的基础结构。
  - 完成后可启动应用并运行空测试集，不依赖案例业务代码。
  - _Requirements: 6.1, 6.2_

- [ ] 1.2 建立数据库迁移与门店/案例表基础
  - 配置迁移工具并创建门店信息表、A3 案例基础表、外键和索引。
  - 门店信息表包含门店名称、品牌标识、品牌名称、业态、门店规模、加盟类型、城市和城市规模等过滤维度；**业务数据由外部同步写入**，迁移脚本可不包含业务种子（本地与 CI 由测试夹具插入镜像行）。
  - 案例表包含案例标识、A3 基础字段、状态、时间戳和门店信息关联，不包含 AI、标签、向量、推荐或反馈字段。
  - 完成后，测试数据库可以应用迁移并查询门店信息表和案例表结构。
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 1.5, 1.6, 3.3, 6.4, 6.5_

- [ ] 2. 实现案例领域核心能力
- [ ] 2.1 定义案例请求、响应和分页契约
  - 定义创建、编辑、删除（基础删除和级联删除）、详情、列表项和分页响应的数据契约。
  - 创建请求包含全部必填基础字段及 **`store_id`**（引用已存在的门店镜像）；**不在请求体中承载**门店画像字段（详情/列表通过关联 `StoreInfo` 返回）；编辑请求禁止修改案例标识和创建时间。
  - 删除契约包含：
    - `DeleteCaseRequest`：包含 `case_id`、`reason`（删除原因枚举）、`requested_by`（删除者标识）
    - `DeleteCaseResponse`：包含 `success`、`deleted_count`、`deleted_at`
    - `CascadeDeleteRequest`：包含 `case_id`、`requested_by`
    - `CascadeDeleteResponse`：包含 `success`、`case_id`、各步骤删除状态和 `partial_failures`
  - 响应契约保留案例标识、状态、过滤字段和更新时间，并排除派生字段。
  - 完成后，API 层和测试可复用同一套请求响应结构。
  - _Requirements: 1.1, 1.3, 1.5, 1.6, 4.5, 5.1, 5.6, 6.1, 7.1, 7.2, 7.3, 7.4_
  - _Boundary: CaseSchemas_

- [ ] 2.2 (P) 实现门店信息、案例持久化模型与状态枚举
  - 建立门店信息模型、A3 案例持久化模型、基础状态和问题类型枚举。
  - A3 案例通过门店信息主键关联门店维度，不在案例表重复保存品牌和门店展示字段。
  - 保证案例标识唯一，创建时间不可变，更新时间可随修改刷新。
  - 完成后模型可表达 `draft`、`active`、`archived` 等基础状态并映射到数据库。
  - _Requirements: 1.1, 1.2, 1.4, 1.5, 1.6, 3.3, 6.5_
  - _Boundary: StoreInfoModel, A3CaseModel_

- [ ] 2.3 (P) 实现字段与步骤校验
  - 校验必填字段与枚举值，并校验解决步骤内容。
  - 校验 `store_id` 在 `store_infos` 中存在（通过 Repository 预检或注入查询结果）。
  - 保留解决步骤顺序，并对非法步骤返回字段级错误。
  - 完成后，非法创建或编辑请求不会进入持久化流程。
  - _Requirements: 2.1, 2.2, 2.3, 3.2, 4.3_
  - _Boundary: CaseValidator_

- [ ] 2.4 实现案例持久化与过滤查询
  - 支持创建、更新、删除、按案例标识查询和按条件分页查询。
  - 创建或编辑案例时校验 `store_id` 在 `store_infos` 中存在；**不对 `store_infos` 执行写入**。
  - 删除操作执行物理删除，返回是否成功删除（受影响行数 > 0）。
  - 支持品牌、门店、业态、门店规模、加盟类型、城市、城市规模、问题类型、状态和创建时间范围过滤。
  - 列表查询使用稳定排序，空结果返回空列表和有效分页信息。
  - 完成后，数据库可保存案例并按 MVP 过滤条件查询。
  - _Requirements: 1.2, 1.5, 1.6, 3.1, 3.3, 4.1, 5.3, 5.4, 5.5, 6.3, 6.5_
  - _Boundary: CaseRepository_
  - _Depends: 2.2_

- [ ] 2.5 实现案例业务服务
  - 编排创建、编辑、删除、详情和列表查询的业务流程。
  - 创建时生成稳定案例标识、基础状态和时间戳；编辑时拒绝不存在、不可编辑或包含不可变字段修改的请求。
  - 删除时支持任意状态的案例，对不存在的案例返回 `CASE_NOT_FOUND`。
  - 校验失败或状态冲突时保留原案例数据。
  - 完成后，服务层可通过独立测试覆盖案例管理核心行为。
  - _Requirements: 2.4, 3.1, 3.3, 3.4, 4.1, 4.2, 4.3, 4.4, 4.5, 5.1, 5.2, 6.1, 6.2, 6.4, 7.4_
  - _Boundary: CaseService_
  - _Depends: 2.1, 2.2, 2.3, 2.4_

- [ ] 2.6 实现级联删除协调器
  - 部署在本规格服务中，作为跨规格级联删除的协调入口。
  - 依次调用本规格的 `CaseService.delete_case` 和下游规格的删除 API（`llm-case-enrichment`、`case-vector-indexing`、`recommendation-feedback`）。
  - 下游服务不可用或删除失败时，不阻塞上游删除，记录失败信息到 `partial_failures`。
  - 支持从案例、案例增强、向量索引节点发起的级联删除（`delete_case_cascade`、`delete_enrichment_cascade`、`delete_vector_cascade`）。
  - 所有删除操作幂等，重复调用不产生副作用。
  - 完成后，前端可通过级联删除 API 一次性清理案例及其派生数据。
  - _Requirements: 6.1, 6.3, 6.6, 6.7_
  - _Boundary: CaseDeleteCoordinator_
  - _Depends: 2.5_

- [ ] 3. 暴露案例管理 API
- [ ] 3.1 实现创建、编辑与删除接口
  - 暴露创建 A3 案例接口，成功时返回案例标识、基础状态和创建时间。
  - 暴露编辑 A3 案例接口，成功时返回更新后的核心字段和更新时间。
  - 暴露基础删除接口（`POST /api/a3-cases/delete`），接受 `DeleteCaseRequest`，返回 `DeleteCaseResponse`。
  - 暴露级联删除协调接口（`POST /api/a3-cases/cascade-delete`），接受 `CascadeDeleteRequest`，返回 `CascadeDeleteResponse`。
  - 完成后，合法创建、编辑和删除请求可通过 HTTP 调用完成持久化变更。
  - _Requirements: 3.1, 3.2, 3.3, 3.4, 4.1, 4.2, 4.3, 4.4, 4.5, 6.1, 6.2, 7.1, 7.2_
  - _Boundary: CaseRouter_
  - _Depends: 2.5, 2.6_

- [ ] 3.2 实现详情与列表查询接口
  - 暴露案例详情接口，返回完整基础字段并处理不存在案例。
  - 暴露案例列表接口，支持门店信息维度过滤、分页和稳定排序。
  - 列表项只返回展示和下游选择所需摘要字段，不返回向量、推荐分值或反馈信息。
  - 完成后，前端或下游服务可通过 HTTP 获取详情和列表候选数据。
  - _Requirements: 1.5, 1.6, 5.1, 5.2, 5.3, 5.4, 5.5, 5.6, 7.1, 7.3, 7.4_
  - _Boundary: CaseRouter_
  - _Depends: 2.5_

- [ ] 3.3 实现统一错误响应
  - 为校验失败、门店不存在（`STORE_NOT_FOUND`）、案例未找到、状态冲突和系统错误提供一致响应结构。
  - 错误响应包含稳定错误码、可读消息和可选字段级详情。
  - 完成后，API 错误不会暴露数据库内部异常，客户端可按错误码处理。
  - _Requirements: 2.2, 2.4, 3.2, 4.2, 4.3, 4.4, 5.2, 6.2, 7.2_
  - _Boundary: ErrorMapper_
  - _Depends: 2.1_

- [ ] 4. 完成应用集成与边界校验
- [ ] 4.1 接入应用入口、数据库会话和路由注册
  - 将案例路由注册到后端应用入口。
  - 为请求生命周期提供数据库会话，并确保事务提交和回滚行为正确。
  - 完成后，从应用入口发起 HTTP 请求即可访问所有案例管理端点。
  - _Requirements: 3.1, 4.1, 5.1, 5.3, 6.1, 7.1_
  - _Boundary: CaseRouter, CaseRepository_
  - _Depends: 3.1, 3.2, 3.3_

- [ ] 4.2 验证案例基础数据与下游派生能力分离
  - 检查模型、请求、响应和列表项均不包含摘要、向量、相似度、推荐理由或反馈字段。
  - 确认响应中保留后续规格需要的案例标识、状态、门店信息过滤字段和更新时间。
  - 完成后，下游规格可以引用基础契约，不会依赖本规格未拥有的派生数据。
  - _Requirements: 1.3, 1.5, 1.6, 5.6, 7.3, 7.4, 7.5_
  - _Boundary: CaseSchemas, StoreInfoModel, A3CaseModel_
  - _Depends: 4.1_

- [ ] 4.3 同步维护详情契约文档与跨规格兼容验证
  - 当 `CaseDetailResponse` 的字段、类型、必填性或枚举语义发生变化时，同步更新 `docs/contract-a3-case-detail-for-enrichment.md` 及其他引用该详情的下游契约文档。
  - 将契约文档更新与跨模块兼容验证纳入交付门禁，确保 `llm-case-enrichment` 等消费者可通过集成测试发现不兼容变更。
  - 完成后，案例详情契约的代码实现、文档说明和下游消费语义保持一致，避免隐式破坏下游集成。
  - _Requirements: 7.3, 7.5_
  - _Boundary: CaseSchemas_
  - _Depends: 4.2_
