# Spec 文档去 AI 味

## 目标

把 Markdown 规格文档改得更像人工写作：直接、自然、重点突出。在不改变原始需求、技术约束和验收标准的前提下，通过重组句式和语义降维，提升文档的可读性。

## 适用范围

* **文档类型**：`requirements.md`、`design.md`、`tasks.md`、`research.md`、验证报告及各类架构决策记录。
* **保护对象**：代码块、命令、路径、配置项、Mermaid 逻辑关系以及表格中的机器可读数据。
* **专业背景**：适配后端微服务 (Spring Cloud, Python, Go) 及移动端（Vue, React）跨平台 (Capacitor) 开发语境。

## 工作流程

1.  **受众识别**：判断文档受众是开发者（保留核心术语）还是业务方（执行彻底的术语降维）。
2.  **结构扫描**：保留原有的标题层级、任务勾选框、追踪关系及 Mermaid 图表结构。
3.  **段落重构**：逐段扫描，识别并拆解西化长句，消除无意义的填充词。
4.  **术语优化**：将抽象的 AI 造词替换为业界通用术语，或改写为具体的职责描述。
5.  **准确性自检**：确认修改后没有模糊性能指标、安全约束或逻辑边界。

## 改写原则

### 1. 句式去西化
* **主动语态优先**：禁止使用“...被执行”，改为“系统执行...”或“由模块 A 触发...”。
* **短句优先**：若一个句子包含超过 3 个“的”或多个嵌套从句，必须拆分；拆开过长定语、嵌套从句和连续修饰语。
* **明确主语**：补全 AI 经常丢失的操作主体（如：开发者、中间件、内核）。
* **中文语序优先**：避免照搬英文结构，例如“对于 X 来说”“基于 Y 的 Z 的实现”。

### 2. 表达实词化
* **删除弱信息词**：剔除“一定程度上”、“相关”、“进行”、“做出”、“基于...的目的”等虚词。
* **口语化与干练并存**：用“负责”、“交给”、“拿到”等词汇替换“归一化”、“持久化操作之执行”等论文式表达。

### 3. 术语专业化
* **禁止硬翻**：保留常用英文术语（如：API, SDK, JSON, Token, Runtime, FFI, Middleware, Bridge）。
* **职责化描述**：遇到抽象概念时，直接描述它“输入什么”、“处理什么”、“输出什么”。

## 常见问题与处理

| AI 常见问题 | 处理方式 | 示例 |
| :--- | :--- | :--- |
| **过度使用“进行”** | 删掉“进行”，直接使用动词。 | 进行初始化 -> 初始化。 |
| **被动语态堆叠** | 改为“对象 + 动作”。 | 数据被推送到前端 -> 将数据推送到前端。 |
| **长定语修饰** | 先定义对象，再说明约束。 | “一个用于处理 X 的 Y 的实现” -> “实现 Y，用于处理 X”。 |
| **状态描述模糊** | 避免“处于...状态”，直接描述结果。 | 处于已连接的状态 -> 已连接。 |
| **因果关系臃肿** | 避免“由于...的原因导致了...”。 | 因为配置错误，所以启动失败。 |

## 示例

### 示例 A：架构职责说明
* **原文**：关于这个被创建的插件桥接层，它被实现化是为了能够让原生端的数据进行向 Web 端的传递操作。这个过程是通过利用特定的信使模式来完成的。
* **改写**：**插件桥接层设计**：该模块负责将原生端数据传递给 Web 端。实现上采用**信使模式**，确保通信异步且非阻塞。

### 示例 B：错误处理规范
* **原文**：领域层推荐返回 `*GeneratorError` 作为分类错误；Runtime 负责归一化未知错误，FFI JSON 契约层仅做稳定映射与脱敏输出。
* **改写**：业务逻辑建议返回 `*GeneratorError`。未知错误交给 Runtime 统一处理。FFI JSON 层不负责业务判断，只负责按固定格式输出数据并完成脱敏。

## 保留与保护清单

* **技术指标**：如 `Latency < 100ms`、`QPS`、内存阈值等精确数值。
* **强度词**：MUST, SHOULD, MAY, REQUIRED 等需求强度标识。
* **Mermaid 语法**：严禁修改图表连线逻辑 (如 `A --> B`) 和节点 ID。
* **格式特征**：EARS 需求格式、验收条件编号、任务状态。
